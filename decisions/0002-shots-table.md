# 0002. シュートの表は 3種類を 1つの CSV にし、シュートのあとに決まる情報とタグ 201 は入れない

- Status: Accepted
- Date: 2026-11-08

## Context
xG のモデルと LLM の予測を同じシュートで比べるため、`events.zip`（7大会・912MB の JSON）からシュートだけを 1行 1本の表に抜き出して、リポジトリに置く（decisions/0001 で「作り方は別の ADR で決める」とした分）。決める必要があったのは次の 4つ。

- シュートは 3種類ある。普通のシュート（43,078本・ゴール 10.4%）、直接フリーキック（2,209本・6.2%）、PK（658本・72.5%）。PK は位置がほぼ同じで、種類だけでほとんど決まる
- 何からのシュートか（クロス・こぼれ球など）は、直前のイベントでわかる。ただ、イングランドの 8,451本では、1つ前のイベントの 3分の 1（2,829本）が相手チームのものだった。多くは守備のデュエルで、Wyscout はデュエルを攻める側と守る側の 2つのイベントに分けて記録しているとみる（推定）
- タグ 201 Opportunity がシュートの 7割に付いている。打つ前の「決定機」なのか、結果を見て付けたのかがわからなかった
- 表のファイルの形（CSV・Parquet・圧縮した CSV）

## Decision
1. 3種類とも表に入れ、`shot_type`（`shot`・`free_kick`・`penalty`）で分ける。xG のモデルは `shot` だけで作る
2. 直前のイベントは、相手チームのイベントを飛ばした、同じ試合・同じ前後半の中の同じチームの 1つ前のイベントにする。表には種類（`prev_event`）と何秒前か（`prev_seconds_before`）の 2列を入れ、何秒前までを使うかはモデルを作るときに決める
3. シュートのあとに決まる情報は入れない: ゴールのどこに飛んだか（タグ 1201〜1223）、枠内か（1801・1802）、ブロックされたか（2101）、終わりの位置（`positions[1]`）、タグ 201 Opportunity
4. CSV にする（`data/shots.csv`）。真偽は 0/1、値がなければ空欄。列の名前・型・意味は `notes/shots-table.md` に書く

`mise run shots` で、`data/raw/events.zip` から作り直せる。同じ元データからは、同じファイルができる。

## Consequences
- フリーキックと PK も同じ表から試せる。LLM と比べるとき、PK のような「答えがほぼ決まっている」シュートで当たり方を確かめることもできる
- 直前のイベントの種類は 33ある。モデルに入れるときに、少ないものをまとめる必要がある
- PK 戦（`match_period` が `P`）のシュートも 76本入っている。xG のモデルや LLM と比べるときに、試合中の PK と分けるかを決める
- 201 を入れないと決めた根拠: 201 のないシュート（12,620本）は、ゴール 0.2%・枠内 1.2%・ブロック 61.8% で、201 のあるシュート（30,458本）のゴール 14.7%・枠内 49.8%・ブロック 8.0% と大きく違う。ゴール 4,492本のうち 4,470本に 201 が付いている。ブロックされずにゴールのほうへ飛んだかを、結果を見て付けた印と推定した
- CSV は 4.1MB。作り直したときに git の差分で変わったところが見え、LLM のプロンプトにもそのまま渡せる。型は残らないので、読むときに列の説明に合わせる（DuckDB などは空欄を NULL として読む）
- 距離・角度などの特徴は、表には入れず、モデルを作るときに位置から出す。表は元データにある値だけにする
- 選ばなかった案
  - フリーキック・PK: 普通のシュートだけを入れる（あとで足すと作り直しになる）、3種類を同じモデルで扱う（PK に引っぱられて、普通のシュートの当たり方が見えにくい）
  - 直前のイベント: 1つ前をそのまま見る（3分の 1 が相手の守備のデュエルになる）、入れない（クロス・スルーパスからのシュートの違いが見えない）
  - 201: 入れて「シュートのあと」の印を付ける（間違えて使うおそれがある）
  - ファイル: Parquet・圧縮した CSV（小さいが、git の差分で中身が見えない）
