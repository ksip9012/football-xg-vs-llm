# 0006. LLM には統計モデルと同じ情報だけを渡して確率を答えさせ、段階を踏んで本数を増やし、同じ物差しと差の幅で比べる

- Status: Accepted
- Date: 2026-11-08

## Context
Step3 の本題は、同じシュートで「統計モデルの xG」と「LLM が答える確率」を比べること。統計モデルの側（decisions/0002〜0005）はそろった。LLM の側で、決める必要があったのは次の 5つ。

1. 何を確かめたいか（問い）
2. 使う LLM
3. シュートの渡し方（どの情報を、どの形で）
4. 何本で試すか（費用）
5. 物差し

## Decision
1. **問い**: 統計モデルと同じ情報だけを渡したとき、LLM はどれだけ当たる確率を言えるか。LLM が持っている「サッカーの常識」が、データから作った xG にどこまで近いかを見る
   - 選手の名前・チーム・試合の日付は渡さない。有名な試合なら、LLM が実際の結果を覚えていて、答えが漏れるおそれがあるため
   - 文章で状況を渡す・結果付きの例を見せる、は本題のあとの追加の試し
2. **LLM**: Gemini 3.8 Flash（Vertex AI、gcloud のログイン）で仕組みを作り、本番のあと、Claude を少ない本数で足す。考える量（thinking）は 500本の試しで LOW・MEDIUM・HIGH を比べて決める（このモデルは MINIMAL を受け付けない）
3. **渡す情報**: まず今の統計モデルと同じ 3つ（ゴールまでの距離 m・ゴールの見える角度（度）・頭か足か）。位置は 0〜100 の割合ではなく、メートルと度に直す。そのあと、両方に直前のプレーとカウンターを足して比べる（統計モデルも作り直す）
   - 送り方: 順番を混ぜて 50本ずつ。`shot_id` は送るときだけ 1 からの連番に置き換える（同じ試合のシュートや、元データの ID の並びから答えが漏れないように）。答えは決まった形の JSON（pydantic のモデル）で受け取る
   - 答えは 1回ごとに `data/llm_runs/` の JSONL に残し、終わった回は飛ばして続きから始める。答えのなかったシュートは、最後にまとめてもう一度だけ送る
4. **本数**: 500本で試す（プロンプト・まとめる本数・考える量を決める）→ 最初の xG と同じテストの 8,626本で本番 → 選手の集計まで並べるなら全部の 42,978本
5. **物差し**: 統計モデルと同じ 4つ（ログ損失・ブライアスコア・AUC・確率の当たり具合）を同じシュートで並べる。差の 95% の幅を、試合単位のブートストラップで出す。LLM ならではのもの（答えられなかった割合・2回聞いたときの揺れ・トークンと費用と時間）と、統計モデルとの相関・差の大きいシュートの地図も見る

## Consequences
- 統計モデルと LLM の違いを、渡す情報の違いではなく「データから学んだか、常識で答えたか」として読める
- LLM の予測は `shot_id, xg` の CSV にすれば、decisions/0005 の集計と図でそのまま並べられる
- 500本の試し（2026-11-08。`notes/llm-trial.md`）の結果、本番は**考える量 LOW・1回に 50本**にした。LOW は MEDIUM・HIGH と物差しがほぼ同じで、HIGH は LOW の 14倍の費用（500本で $0.69）と 13倍の時間がかかった。LOW の 500本は $0.05・70秒ほど。答えの抜けと形の崩れは 2,000本で 0
- 500本では、Gemini は統計モデルとほぼ同じくらい当て（相関 0.98）、確率は全体に低めだった。差が偶然かは本番で確かめる
- 本番（テストの 8,626本、2026-11-08。`notes/llm-test.md`）では、差の 95% の幅が 3つの物差しとも 0 をまたいだ（AUC の差 −0.0007、幅 −0.0043〜+0.0026）。当たり方の差は見分けられない。Gemini の確率は全体に低め（平均 0.092、実際 0.104）で、12〜18m でいちばん低い。費用 $0.85・21分
- 両方に直前のプレーとカウンターを足した比べ（2026-11-15。decisions/0007、`notes/llm-context.md`）では、統計モデルは少しよくなり（ログ損失の差の幅 −0.0037〜−0.0000）、Gemini はよくならなかった。広い情報どうしでは、ログ損失とブライアスコアで統計モデルのほうがよいと見分けられた。費用 $0.97
- GCP は、手元の `mise.local.toml`（git の外）に `GOOGLE_CLOUD_PROJECT` と `GOOGLE_CLOUD_QUOTA_PROJECT` を書く。gcloud のログイン（ADC）の quota project がほかのプロジェクトになっていると、Vertex AI が「API が有効でない」と返すため
- 選ばなかった案
  - 問い: 文章で状況を渡す（文章を作る部分で条件がずれる）、結果付きの例を見せる（例の選び方で結果が大きく変わる）。どちらも追加の試しにした
  - LLM: Gemini だけ（「LLM は」と言える範囲が 1つのモデルに限られる）、同じ会社の大きさ違い（料金が高い）
  - 渡す情報: 最初から広い情報（統計モデルを先に作り直す手間）
  - 本数: 最初から全部（プロンプトを直すたびに全部の料金がかかる）、テストだけで終える（選手の集計を並べられない）
  - 物差し: 4つだけ（差が偶然かと、LLM のくせが見えない）、理由も書かせる（出力が増えて料金が数倍になる。500本の一部で聞く形は残す）
