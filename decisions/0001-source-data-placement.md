# 0001. 元データはすべて落として使い、zip は展開せずに読む

- Status: Accepted
- Date: 2026-11-04

## Context
Wyscout の公開データ（Pappalardo ほか 2019、figshare の Soccer match event dataset v5）から、シュートが決まる確率（xG）を作る。元データは 10 ファイルで、ライセンスはどれも CC BY 4.0（出典を書けば、複製・配布・改変ができる）。

- `events.zip` が 77MB で、展開すると 7大会で 912MB の JSON になる。シュートは 43,078 本で、残りはパス・デュエルなど
- ほかは小さい（`matches.zip` 0.6MB、`playerank.json` 6.2MB、`players.json` 1.7MB、残りは 200KB 以下）
- figshare は版ごとに DOI が付いていて（v5、2020-01-28）、同じ URL のファイルが差し替わることは少ないとみる
- `referees.json` は、配布元のファイルが途中で切れている（figshare に載っている大きさと同じ）

元データをリポジトリに入れるか、使うたびに落とすか、zip を展開して置くかを決める必要があった。

## Decision
元データはすべてリポジトリに入れず、`mise run fetch` で落として `data/raw/`（git の対象外）に置く。

- `data/sources.toml` に、ファイルごとの URL（figshare のダウンロード用 URL）と sha256 を書く。落としたファイルが一覧と同じかを sha256 で確かめる
- `events.zip`・`matches.zip` は展開しない。Python の `zipfile` で、中のファイルを直接読む
- 元データから作る表（シュートの表など）は、小さいのでリポジトリに入れる。作り方は別の ADR で決める
- README に出典（論文と figshare）とライセンス（CC BY 4.0）を書き、作った表は元データを加工したものだと書く

## Consequences
- リポジトリは大きくならない。展開しないので、手元のディスクも 86MB ほどで済む
- figshare のファイルが差し替わったら、sha256 が合わずに止まるので気づける
- figshare が使えなくなると、元データを落とし直せない。ただし、作った表はリポジトリにあるので、分析と比べる作業は続けられる
- zip の中の大会ごとの JSON（最大 190MB ほど）は、1つずつメモリに読み込む。この Mac（メモリ 16GB）では足りる見込み
- 選ばなかった案: 元データをリポジトリに入れる（CC BY 4.0 なので入れられるが、77MB の zip で履歴が重くなる）、展開して置く（912MB になり、使うのはシュートなどの一部だけ）、小さなファイルだけ入れる（Step2 と違い、元データが消える心配が小さく、置き方が 2通りになるだけ）
